# Runner version notes — 2026-11-15

**Audience:** Dash (Bilge), Deploy (Ceyda) and their coding agents.
**Scope:** A failed job can now be run again on its own with `RetryJob`, as a new attempt in the same pipeline. Because a retried pipeline finishes again, `PipelineFinished` can now arrive more than once for one pipeline. Migration 006 adds the attempt columns and the `ci_svc.inbox` table of ADR 0010. Container images for ci-svc and git2-runner now build for amd64 and arm64.

**Canonical reference:** [docs/api/pipelines.md → RetryJob](../../../api/pipelines.md#retryjob), [docs/api/events.md → PipelineFinished](../../../api/events.md#civ1pipelinefinished), [docs/api/config.md → Images](../../../api/config.md#images) and [docs/api/runners.md → Installing a runner](../../../api/runners.md#installing-a-runner).
The API docs are the source of truth; this note only summarizes the change.

**Breaking?** No. A consumer that keeps the latest `PipelineFinished` per pipeline already works.

---

## 🟢 NEW — `RetryJob`

The "Retry" button on a failed job. It adds attempt 2 (3, …) of the job to the **same** pipeline. The earlier attempt keeps its status and its log.

```sh
grpcurl -plaintext -d '{"jobId": "<job-id>", "idempotencyKey": "<uuid-made-on-click>", "triggeredById": "<user-id>"}' \
  localhost:9090 ci.v1.PipelineService/RetryJob
# {"job": {"id": "<new-id>", "name": "unit", "status": "JOB_STATUS_PENDING", "attempt": 2, "retryOfId": "<job-id>", …},
#  "pipeline": {"status": "PIPELINE_STATUS_RUNNING", …}, "created": true}
```

- Later-stage jobs that never ran (`SKIPPED`, or `CANCELED` before they started) get new attempts too, so the pipeline continues.
- `GetPipeline` and `ListPipelines` show the newest attempt of each job. `Job` has two new fields: `attempt` (1 for the first run) and `retry_of_id`.
- `GetJob` and `StreamJobLog` still serve old attempts. Follow `retry_of_id` to list them.

| Code | When |
|---|---|
| `FAILED_PRECONDITION` | The pipeline has not finished; the job is not the newest attempt; the job was `SKIPPED`; or an earlier stage did not succeed |
| `ALREADY_EXISTS` | The key was used to retry another job |
| `INVALID_ARGUMENT`, `NOT_FOUND` | Bad IDs or key; unknown job |

Retrying a **whole** pipeline is unchanged: `TriggerPipeline` with a new key ([8 Nov](08_11.md)).

## 🟡 CHANGED — `PipelineFinished` can repeat

| Before | Now |
|---|---|
| Once per pipeline | Each time the pipeline finishes. After `RetryJob` it runs and finishes again, with a new `eventId` |
| `JobFinished` once per job | Once per attempt; an attempt has its own `jobId` |

## ℹ️ FYI — migration 006

git2 gets `migrations/006_ci_inbox_and_attempts.sql` (004 and 005 are auth-svc's). It adds `attempt`, `retry_of`, `idempotency_key` and `triggered_by` to `ci_svc.jobs`, and the `ci_svc.inbox` table for pushes delivered through `EventSink` (ADR 0010; the worker that reads it comes with #20). ci-svc refuses to start until 006 is applied.

## 🟢 NEW — images for ci-svc and git2-runner

`app/Dockerfile` builds both programs for `linux/amd64` and `linux/arm64`: static binaries on distroless, user 65532, about 6–10 MB. CI builds them on every pull request. They are **not published yet**; the proposed names are `ghcr.io/git2-project/ci-svc` and `ghcr.io/git2-project/git2-runner` (WBS-13.4, #40).

| Image | Ports | Volume | Configured by |
|---|---|---|---|
| `ci-svc` | `9090` internal, `9091` runners | none | the variables in [config.md](../../../api/config.md) |
| `git2-runner` | none | `/etc/git2-runner` (holds the runner token) | `register` once, then `run`; needs a Docker daemon |

The runner can also run as a systemd service: [`deploy/systemd/git2-runner.service`](../../../../deploy/systemd/git2-runner.service).
