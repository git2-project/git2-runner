# Runner version notes — 2026-11-18

**Audience:** Deploy (Ceyda), Dash (Bilge), Codeplane (Apo) and their coding agents.
**Scope:** A `git push` now starts pipelines by itself. ci-svc serves `events.v1.EventSink` on its internal port, stores each `git.v1.RepositoryPushed` that codeplane's relay delivers, and starts one pipeline per pushed branch or tag. This was tested end to end with a real push to git-svc `v0.3.0` and a runner that ran the jobs.

**Canonical reference:** [docs/api/pipelines.md → TriggerPipeline](../../../api/pipelines.md#triggerpipeline) (the "For pushes" part), [docs/api/overview.md → Two ports](../../../api/overview.md#two-ports) and [docs/api/config.md](../../../api/config.md).
The API docs are the source of truth; this note only summarizes the change.

**Breaking?** No. Nobody called `TriggerPipeline` for pushes, and that RPC is unchanged for manual runs.

## 🟢 NEW — a push starts its pipelines (`events.v1.EventSink`)

```
git push ──► git-svc ──outbox──► relay ──Deliver──► ci-svc :9090 ──► ci_svc.inbox
                                                                     │ worker
                                    GetBlob(.git2-ci.yml @ new_sha) ◄┘
                                                                     └──► pipeline + jobs ──► runner
```

- **`Deliver` only stores the event** and answers `OK`. A repeat of the same `event_id` changes nothing. A type other than `git.v1.RepositoryPushed`, or a payload that is not one, gets `INVALID_ARGUMENT`, so the relay stops sending it. Any other failure (database down) is `INTERNAL`, and the relay retries.
- **A worker then starts the pipelines**, once per created or moved branch or tag (`refs/heads/*`, `refs/tags/*`):
  - `commit_sha` is the commit at the ref's `new_sha`. For an annotated tag, `new_sha` is the tag object, and the pipeline records the commit it points to (git-svc reports it with the file). `trigger` is `PIPELINE_TRIGGER_PUSH`, and `triggered_by_id` is the event's `pusher_id`;
  - the idempotency key is `"<event_id>:<ref>"`, so a redelivered event never starts a pipeline twice;
  - deleted refs, `refs/notes/*` and commits without `.git2-ci.yml` start nothing.
- **A push is never lost on our side.** If git-svc or the database cannot be reached, the event waits in `ci_svc.inbox`. It is tried again after 5 s, then 10 s, 20 s, and so on, at most every 5 minutes. Handled events are deleted after 7 days.
- **Speed.** Measured on one machine: push at 15:32:26.98, `Deliver` at 27.61, both pipelines created by 27.72. That is under a second.

What we ran on 18 Nov:
- git-svc built from git2-codeplane `v0.3.0`, with `GIT2_GITSVC_EVENT_SINKS=<ci-svc>:9090=git.v1.RepositoryPushed`;
- ci-svc from this change, and one `git2-runner` on Docker;
- a push of `main`, tag `v0.1.0` and a branch without `.git2-ci.yml`.

The result: two pipelines (`main` and `v0.1.0`) with the pusher recorded, none for the third branch. All four jobs passed, and the log reads `hello from git2 CI`.

## ℹ️ FYI — a restarted runner removes what its crashed jobs left behind

For whoever runs build hosts. Every container, network and volume a job creates now also carries `io.git2.runner-id=<runner_id>`. When a runner starts, it removes everything with its own ID, which is what its jobs left behind when it or its host died, and logs the names. Other runners on the same Docker daemon are never touched. Never run two runners with the same config on one daemon. See [runners.md → After a crash](../../../api/runners.md#after-a-crash) (git2-runner #30).
