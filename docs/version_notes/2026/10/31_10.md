# Runner version notes — 2026-10-31

**Audience:** Codeplane (Apo) and every lane reading the 29 Oct note, and their coding agents.
**Scope:** Fixes from Apo's review of git2-runner PR #28, before it is merged: longer idempotency keys, the push and event delivery path marked as open, and a lock-order fix in ci-svc. After the merge: three runner fixes found by its new unit tests.

**Canonical reference:** [docs/api/pipelines.md → TriggerPipeline](../../../api/pipelines.md#triggerpipeline) and [docs/api/events.md → Delivery](../../../api/events.md#delivery).
The API docs are the source of truth; this note only summarizes the change.

**Breaking?** No. Nothing was merged yet, and the key limit only got wider.

---

## 🟡 CHANGED — `idempotency_key` accepts any ref name

| | Before | Now |
|---|---|---|
| `TriggerPipelineRequest.idempotency_key` | 1–200 printable ASCII characters | 1–512 bytes of UTF-8 text without control characters |

The recommended push key `"<event_id>:<ref>"` was refused for refs with non-ASCII names (`refs/heads/feature/café`) or longer than about 160 bytes, so CI never started for those pushes. Now it fits every ref `TriggerPipeline` accepts (at most 255 bytes). `ref` must now also be valid UTF-8; invalid bytes are `INVALID_ARGUMENT` instead of an internal error.

## 🟡 CHANGED — How pushes and events travel is not decided yet

The 29 Oct note said "the relay calls `TriggerPipeline`" and "the relay reads `ci_svc.outbox`". Those were proposals. A relay reading other services' schemas would break the one-schema-per-service rule (codeplane ADR 0006). Both are now marked **to be agreed** in the WBS-1.3 design (W2), and the 29 Oct action items say so. What does not change: delivery is at least once, and `TriggerPipeline` is idempotent.

## ℹ️ FYI — Inside ci-svc

- Canceling a pipeline while one of its jobs reported its result could deadlock in PostgreSQL. It was retried, so no call failed, but it cost about a second. `CancelPipeline` now locks jobs in stage order, and a new test covers the race ([ADR 0006](../../../decisions/0006-job-queue-and-lifecycle.md), "Locks").
- Devcontainer: the test PostgreSQL gets three minutes for its first start, which was too slow on a Windows host.
- Assumption A-12 (IDs, not names) is confirmed.

## ℹ️ FYI — Runner fixes found by its unit tests

The runner's job loop and log upload now have unit tests (issue #29). They found three bugs, all fixed. No lane has anything to do.

- **A runner could hang for good.** When ci-svc took a job away (its lease ran out, or an admin deleted the runner), the runner stopped the job but kept resending its log, which ci-svc refused, and never asked for another job. It now drops that log and goes on.
- **A job could be dropped at shutdown.** If a SIGTERM came at the moment a `RequestJob` reply brought a job, the runner exited without running it, and the job failed as `RUNNER_LOST` a minute later. The runner now runs that job first, like any job it already holds.
- **No retries after `UNAUTHENTICATED`.** A runner deleted just before it reported a result used to retry the report for about 30 seconds. It now stops at once.
